# M5c1: TLS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One certificate in the config file secures the server: HTTPS for the API and for the media listener, an RTMPS listener (publish and play), an RTSPS listener (play, RTP interleaved inside TLS), and TLS clients for RTMPS pull, RTMPS push and RTSPS pull, with the certificate replaced on disk taken up without a restart.

**Architecture:**
- **`internal/certs`** holds the one certificate pair behind an atomic pointer. Every TLS listener's `tls.Config` reads it through `GetCertificate`, so a reload is one pointer swap and no listener is touched. A poll of the two files and every config reload feed it.
- **TLS is a second listener beside each plain one** (`tls_listen` next to `listen`), served by the same handler: the same `http.Server` for media and for the API, the same `rtmpplay.Server` registered on a second `rtmpsrv` listener, the same `rtspplay.Server` serving a second `net.Listener`. A stream's outputs, gates and metrics do not know which listener a player came through.
- **Clients:** `pkg/rtmp` and `pkg/rtsp` learn the `rtmps://` and `rtsps://` schemes and take a `*tls.Config`. `internal/ingest` and `rtmppush` add our own spelling of the opt-out, the scheme suffix `+insecure`, and translate it before the library sees the URL.
- **The hub is untouched.** TLS wraps connections at the edge. Nothing here reads or writes a hub differently, and no write to a hub can block on a handshake.

**Tech Stack:** Go 1.26, stdlib only (`crypto/tls`, `crypto/x509`, `net/http`). Peers: ffmpeg 8 on the host; ffmpeg 6.1, VLC 3.0.20 and GStreamer 1.24 in `osv2-ci-peers:m4a`.

**Spec:**

## Rulings (R-S)

Each ruling ends with what it costs if it is wrong.

- **R-S1 (the split; the controller's ruling, binding).** M5c is two plans.
  - **M5c1 (this plan), TLS:** the certificate in the config file; HTTPS for the API and the media listener; an RTMPS listener (publish and play); RTMPS pull and push; an RTSPS listener (play only, TCP only) and RTSPS pull.
  - **M5c2 (a later plan):** SRTP for RTSP over UDP, SRT output encryption, credentials in URL paths, secrets as write-only spec fields. See "Out of M5c1".
  - **M5c1's exit criterion:** ffmpeg publishes over RTMPS and plays over RTMPS, RTSPS and HTTPS (HLS, DASH, HTTP-TS) against our server; our server pulls from and pushes to a peer over RTMPS and pulls RTSPS.
  - *If wrong:* M5c2 finds that SRTP needs a different listener shape. R-S6 keeps that open: RTSPS today refuses UDP, which is exactly the hole SRTP fills.
- **R-S2 (one certificate).** `server.tls` holds one pair, `cert_file` and `key_file` (PEM; the certificate file may carry the chain). Every TLS listener presents it. A certificate that must cover several names carries them as SANs.
  - Paths are used as given, like `assets_dir`. The key file's mode is not checked: certbot's layout is the operator's.
  - Minimum version TLS 1.2. No client certificates.
  - *If wrong:* an operator who needs a different certificate per listener or per SNI name runs a TLS proxy in front until a later milestone adds a per-listener override; the key names leave room for it (`server.http.tls` beside `server.http.tls_listen`).
- **R-S3 (the certificate reloads without a restart, two ways).**
  - **By polling:** every 30 s the server stats both files (`os.Stat`, which follows certbot's `live/` symlinks) and, when a size or a modification time changed, reads the pair again.
  - **By reload:** `SIGHUP` and `POST /api/v1/reload` read the pair again first, whatever the config reload then does.
  - A pair that does not load (a key that does not match its certificate because a rotation is half done, an unreadable file, bad PEM) keeps the certificate in force, is counted and is logged once per distinct error; the next poll tries again. An expired certificate that loads is taken and logged as a warning: the files are the operator's word.
  - New handshakes get the new certificate; sessions in flight are not touched.
  - **What still needs a restart:** a change to `server.tls.cert_file`, `server.tls.key_file` or any `tls_listen`. They are reported as `restart_required` like every other `server` key (R-D4). Only the *content* of the files is live.
  - No file-watch library: stdlib only.
  - *If wrong:* a rotation is taken up to 30 s late; an operator who cannot wait sends `SIGHUP`.
- **R-S4 (HTTPS is a second listener; plain HTTP stays).**
  - `server.http.tls_listen` and `server.api.tls_listen` each open a TLS listener that serves the same handler as its plain sibling. Neither has a default: empty is off.
  - `server.http.listen` keeps its default `:8080`. Plain HTTP is not redirected and gets no HSTS header: LAN players, health checks and an `http://` HLS pull keep working.
  - HTTP/1.1 only on the TLS listeners (`TLSNextProto` set to an empty map). HTTP-TS is one long response whose slow-reader rule is a per-write deadline, proved over HTTP/1.1 only.
  - A `tls_listen` without `server.tls` is a config error, and so is `cert_file` without `key_file` or the reverse.
  - *If wrong:* a browser fetches segments over up to six HTTP/1.1 connections instead of one HTTP/2 connection. HTTP/2 is a backlog item with its proof named (the HTTP-TS deadline under HTTP/2 flow control).
- **R-S5 (R-D8 after TLS: the API's default does not move).**
  - `server.api.listen` stays plain and stays `127.0.0.1:8081` by default. Configuring a certificate never exposes the control plane by itself.
  - The network-facing API is `server.api.tls_listen`, opt-in, with no default port.
  - A plain `api.listen` beyond loopback is still allowed and still warned about at start (a reverse proxy or a container network is a legitimate reason); the warning now names `server.api.tls_listen` as the fix.
  - *If wrong:* an operator who expected "a certificate turns HTTPS on" sets one more key. The opposite mistake would publish Basic credentials' endpoint to the internet on an upgrade.
- **R-S6 (RTMPS and RTSPS listeners).**
  - `server.rtmp.tls_listen` and `server.rtsp.tls_listen`, sharing `app` with their plain siblings. Either sibling may be off; `outputs.rtmp` or `outputs.rtsp` needs at least one of its two listeners.
  - **RTMPS play:** `rtmps://host:port/<app>/<name>`, the same play handler and caps as RTMP.
  - **RTMPS publish:** an input `rtmps://<the server's RTMPS address>/<app>/<key>?mode=listen`. It must name the server's RTMPS listener: a stream cannot open a TLS listener of its own, because the certificate is the server's. The default port of `rtmps://` is 443.
  - A plain `rtmp://…?mode=listen` input on the RTMPS address, and the reverse, are refused as an address conflict.
  - **RTSPS play:** `rtsps://host:port/<app>/<name>`, TCP only: a `SETUP` that offers only UDP is answered 461, even when `server.rtsp.udp` is on. R-D1's SRTP is M5c2.
  - The TLS handshake runs in the session's goroutine under the protocol's existing pre-session deadline (RTMP's 5 s handshake timeout, RTSP's read timeout and pending lifetime), never in an accept loop, and counts against the existing pre-session caps.
  - *If wrong:* a publisher that needs RTMPS on a second port waits for a per-listener certificate (R-S2).
- **R-S7 (TLS clients verify; the opt-out is in the scheme).**
  - `rtmps://` (pull and push; default port 443) and `rtsps://` (pull; default port 322) verify the peer against the system roots, with the URL's host as the server name. A private CA is added to the system store or named with `SSL_CERT_FILE`, which Go's `crypto/x509` reads on Unix.
  - **The opt-out is `rtmps+insecure://` and `rtsps+insecure://`.** It turns certificate verification off for that one URL and nothing else. It is not a default and no config key sets it globally. `+insecure` on any other scheme is refused, and so is `rtmps+insecure://…?mode=listen`.
  - Why the scheme: a stream's input and push are identified by their URL (`Pipeline.SetInputs`, the pushers' map), so the choice must be part of the URL; a query parameter cannot be used, because a push sends its query to the target verbatim (`rtmp.Config.KeepQuery`); a scheme is never sent to the peer (the `tcUrl` says `rtmps://`).
  - `pkg/rtmp` and `pkg/rtsp` know only `rtmps://` and `rtsps://` and a `*tls.Config`. The `+insecure` spelling is the product's, in `internal/ingest` and `rtmppush`.
  - `rtsps://` uses the TCP transport: `transport=udp` is refused at parse, `auto` means TCP.
  - A verification failure is an ordinary open failure: the input retries or fails over, the push backs off, and the error names the x509 reason and never the URL's secrets.
  - *If wrong:* the spelling is odd to someone used to a flag, and renaming it later is a config migration. IP cameras with self-signed certificates make some opt-out necessary.
- **R-S8 (closing a TLS connection never waits on the peer).** `tls.Conn.Close` sends `close_notify` under its own 5 s write deadline, so one stalled player can hold a teardown for 5 s. Every close of a TLS connection we own (RTMP and RTSP, server and client) sends `close_notify` on a best-effort basis and closes the raw connection after at most 100 ms. `net/http` keeps its own rule.
  - *If wrong:* a peer that reads slowly sees a truncated TLS stream at the end and logs it; no media is lost, because each protocol has its own end-of-stream message.
- **R-S9 (secrets).** An `rtmps://` or `rtmps+insecure://` URL is redacted exactly as an `rtmp://` one (the stream key cut to two characters, `redact.URL`, `redact.Masked`, the push scrubber, `logging.Scrub`). The key file's content is never read into an error, a log or a response; its path is not a secret.

## Global Constraints

- **Libraries:** stdlib only (`crypto/tls`, `crypto/x509`, `net/http`). No new module; `go mod tidy` changes nothing. Never bluenviron or lal as a library, and never another product's code. Approved existing dependencies: mp4ff, pion/rtp, pion/sdp, datarhei/gosrt, testify, go-astiav, protowire, go.yaml.in/yaml/v3.
- **Frozen behaviour:** with no `server.tls` and no `tls_listen`, the server binds, serves, logs and reports exactly what it does at HEAD 0b31565. Every existing test passes unchanged, except rows that assert `rtsps` or `rtmps` is refused.
- **House rules:**
  - the hub is the only data source and hub writes never block;
  - hot reload goes by diff: every new `server` key is `restart_required`; only the certificate files' content is live (R-S3);
  - errors are `module: op: %w`, never both logged and returned;
  - every goroutine has a cancel path;
  - all configuration is the one YAML file, rewritten atomically by API writes;
  - no secret in a log, a metric or a response (R-S9).
- **Lint:** `exhaustive`, `godot`, gofumpt.
- **Tests:**
  - bind `127.0.0.1:0` only; never 554, 1935 or 8554 (nor 322 or 443);
  - certificates are generated in-process by `certstest` from a test CA; no private key is checked in;
  - every peer test passes on the host (ffmpeg 8) and in `make test-ci-peers` before any push;
  - the arm64 job has only ffmpeg and sets `OS_REQUIRE_PEERS=1`.
- **Environment:** the v1 soak containers (open-streamer-soak-mediamtx, caddy, grafana, osdev-console-1, vector, alloy, pyroscope, prometheus, node-exporter, nvidia-gpu-exporter) are never stopped, restarted or reconfigured. Own containers are named `osv2-*` and run with `--rm`. No GPU work.

## Review Focus

1. **A rotation that is half done, and one behind a symlink.** The certificate file is replaced before the key file, or certbot retargets `live/` symlinks: the server keeps serving the old pair, counts one failure, logs it once without any key material, and takes the new pair on a later poll, with no restart and no session ended. *Pinned by Task 1's `TestStoreReloadKeepsOld` and `TestStoreWatchSymlink`, and Task 9's `TestCertificateRotates`.*
2. **The wrong protocol, or silence, on a TLS port.** A plaintext RTMP or RTSP client on the TLS port, a TLS client on the plain port, a client that connects and sends nothing, and a client that stops mid-handshake: each is closed by the existing pre-session deadline, counted in the existing pre-session caps, never stalls the accept loop for other clients, and a plain HTTP request to the HTTPS port gets 400. *Pinned by Task 4's `TestServeTLSWrongProtocol`, Task 5's `TestRegistryTLSWrongProtocol` and Task 9's `TestHTTPSWrongProtocol`.*
3. **A stalled TLS peer at teardown.** A player whose socket buffer is full while its stream is deleted or the server stops: its close returns within 1 s, not `tls.Conn`'s 5 s (R-S8). *Pinned by Task 3's `TestTLSCloseStalled`, Task 4's `TestServeTLSCloseStalled` and Task 5's `TestRegistryTLSUnregisterStalled`.*
4. **A source whose certificate cannot be verified.** Self-signed, expired, or issued for another name: the pull or push fails with the x509 reason and no secret, retries as any failed open does, and is never silently accepted; `+insecure` accepts it for that URL only; `+insecure` on `rtmp://`, `http://` or a listen input is refused at validation. *Pinned by Task 3's `TestPlayTLSVerifies`, Task 6's `TestPushTLS`, Task 7's `TestParseTLSSchemes` and `TestTLSPullUntrusted`.*
5. **A stream key in an `rtmps://` URL.** `rtmps://h/live/<key>`, `rtmps+insecure://u:p@h/live/<key>?token=<t>` and `RTMPS://…`: the key, the password and the token are masked wherever an `rtmp://` URL's are, a masked URL is refused on the way back in, and the scheme is kept. *Pinned by Task 2's `TestURLTLSSchemes`, Task 6's `TestPushTLS` and Task 10's `TestM5c1NoSecretsLeak`.*

## Hand-over: M5c2

M5c2 starts from these facts of M5c1:
- An RTSPS session refuses UDP with 461 (`pkg/rtsp` `ServeTLS`, R-S6). SRTP adds `RTP/SAVP` offers to exactly that branch, with keys carried in the SDP that only a TLS session sees.
- The certificate store and the listener keys are not SRT's: SRT output encryption is a passphrase, as the input's is.
- `redact` treats the three RTMP schemes alike (`redact.RTMPScheme`); credentials in other URL paths have no rule yet.
- The config status and every stream document still return stored secrets to an editor (`?secrets=1`, `GET /api/v1/config`): write-only fields change that contract, not this plan.
