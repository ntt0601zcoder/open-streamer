# M5c1: TLS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One certificate in the config file secures the server: HTTPS for the API and for the media listener, an RTMPS listener (publish and play), an RTSPS listener (play, RTP interleaved inside TLS), and TLS clients for RTMPS pull, RTMPS push and RTSPS pull, with the certificate replaced on disk taken up without a restart.

**Architecture:**
- **`internal/certs`** holds the one certificate pair behind an atomic pointer. Every TLS listener's `tls.Config` reads it through `GetCertificate`, so a reload is one pointer swap and no listener is touched. A poll of the two files and every config reload feed it.
- **TLS is a second listener beside each plain one** (`tls_listen` next to `listen`), served by the same handler: the same `http.Server` for media and for the API, the same `rtmpplay.Server` registered on a second `rtmpsrv` listener, the same `rtspplay.Server` serving a second `net.Listener`. A stream's outputs, gates and metrics do not know which listener a player came through.
- **Clients:** `pkg/rtmp` and `pkg/rtsp` learn the `rtmps://` and `rtsps://` schemes and take a `*tls.Config`. `internal/ingest` and `rtmppush` add our own spelling of the opt-out, the scheme suffix `+insecure`, and translate it before the library sees the URL.
- **The hub is untouched.** TLS wraps connections at the edge. Nothing here reads or writes a hub differently, and no write to a hub can block on a handshake.

**Tech Stack:** Go 1.26, stdlib only (`crypto/tls`, `crypto/x509`, `net/http`). Peers: ffmpeg 8 on the host; ffmpeg 6.1, VLC 3.0.20 and GStreamer 1.24 in `osv2-ci-peers:m4a`.

**Spec:**
- `docs/REBUILD_PLAN.md` §5, the M5c row: "Transport security: HTTPS for the API and the HTTP outputs, RTMPS (listen, pull, push), RTSPS and SRTP, SRT encryption (input and output), credentials in URL paths and queries redacted, secrets as write-only spec fields". Exit: "ffmpeg publishes and plays over each secured protocol against our server; no secret appears in a response, a log or a metric".
- `docs/superpowers/plans/2026-11-26-m5a-control-plane-core.md`: R-D1 ("RTSPS with SRTP by its own ruling"), R-D4 (a `server` change needs a restart), R-D8 (the API listens on loopback until M5c).

## Rulings (R-S)

Each ruling ends with what it costs if it is wrong.

- **R-S1 (the split; the controller's ruling, binding).** M5c is two plans.
  - **M5c1 (this plan), TLS:** the certificate in the config file; HTTPS for the API and the media listener; an RTMPS listener (publish and play); RTMPS pull and push; an RTSPS listener (play only, TCP only) and RTSPS pull.
  - **M5c2 (a later plan):** SRTP for RTSP over UDP, SRT output encryption, credentials in URL paths, secrets as write-only spec fields. See "Out of M5c1".
  - **M5c1's exit criterion:** ffmpeg publishes over RTMPS and plays over RTMPS, RTSPS and HTTPS (HLS, DASH, HTTP-TS) against our server; our server pulls from and pushes to a peer over RTMPS and pulls RTSPS.
  - *If wrong:* M5c2 finds that SRTP needs a different listener shape. R-S6 keeps that open: RTSPS today refuses UDP, which is exactly the hole SRTP fills.
- **R-S2 (one certificate).** `server.tls` holds one pair, `cert_file` and `key_file` (PEM; the certificate file may carry the chain). Every TLS listener presents it. A certificate that must cover several names carries them as SANs.
  - Paths are used as given, like `assets_dir`.
  - On Unix a key file that its group or others can read (`mode & 0o077 != 0`) gets one warning at start and is never refused: a Kubernetes secret mount is 0644 or 0444 and must keep working.
  - Minimum version TLS 1.2. No client certificates.
  - *If wrong:* an operator who needs a different certificate per listener or per SNI name runs a TLS proxy in front until a later milestone adds a per-listener override; the key names leave room for it (`server.http.tls` beside `server.http.tls_listen`).
- **R-S3 (the certificate reloads without a restart, two ways).**
  - **By polling:** every 30 s the server stats both files (`os.Stat`, which follows certbot's `live/` symlinks) and reads the pair again when a size or a modification time changed, **and on every tick while the latest read failed**. The second rule covers what a stat cannot see: a `chmod` that makes the key readable again, and a rewrite of the same size within one tick of the file system's clock.
  - **By reload:** `SIGHUP` and `POST /api/v1/reload` read the pair again first, before they take the config lock, whatever the config reload then does: a certificate reload never queues behind a slow apply.
  - A pair that does not load (a key that does not match its certificate because a rotation is half done, an unreadable file, bad PEM) keeps the certificate in force, is counted and is logged once per distinct error; every later tick tries again until one succeeds. A read that finds the same leaf is counted as `unchanged` and logs nothing. An expired certificate that loads is taken and logged as a warning: the files are the operator's word.
  - New handshakes get the new certificate; sessions in flight are not touched.
  - **What still needs a restart:** a change to `server.tls.cert_file`, `server.tls.key_file` or any `tls_listen`. They are reported as `restart_required` like every other `server` key (R-D4). Only the *content* of the files is live.
  - No file-watch library: stdlib only.
  - *If wrong:* a rotation is taken up to 30 s late; an operator who cannot wait sends `SIGHUP`.
- **R-S4 (HTTPS is a second listener; plain HTTP stays).**
  - `server.http.tls_listen` and `server.api.tls_listen` each open a TLS listener that serves the same handler as its plain sibling. Neither has a default: empty is off.
  - `server.http.listen` keeps its default `:8080`. Plain HTTP is not redirected and gets no HSTS header: LAN players, health checks and an `http://` HLS pull keep working.
  - HTTP/1.1 only on the TLS listeners (`TLSNextProto` set to an empty map). HTTP-TS is one long response whose slow-reader rule is a per-write deadline, proved over HTTP/1.1 only.
  - A `tls_listen` without `server.tls` is a config error, and so is `cert_file` without `key_file` or the reverse.
  - The proof of HTTP/1.1 is a client that offers `h2`: ALPN must still pick `http/1.1` (Task 9a).
  - *If wrong:* a browser fetches segments over up to six HTTP/1.1 connections instead of one HTTP/2 connection. HTTP/2 is a backlog item with its proof named (the HTTP-TS deadline under HTTP/2 flow control).
- **R-S5 (R-D8 after TLS: the API's default does not move).**
  - `server.api.listen` stays plain and stays `127.0.0.1:8081` by default. Configuring a certificate never exposes the control plane by itself.
  - The network-facing API is `server.api.tls_listen`, opt-in, with no default port.
  - A plain `api.listen` beyond loopback is still allowed and still warned about at start (a reverse proxy or a container network is a legitimate reason); the warning now names `server.api.tls_listen` as the fix.
  - **Exposing the API has a precondition** (controller ruling; `docs/REBUILD_PLAN.md` 1529–1533): the login limiter gets a per-address cap on verifications in flight in this plan (R-S10), because `server.api.tls_listen` is the exposure that note waits for.
  - *If wrong:* an operator who expected "a certificate turns HTTPS on" sets one more key. The opposite mistake would publish Basic credentials' endpoint to the internet on an upgrade.
- **R-S6 (RTMPS and RTSPS listeners).**
  - `server.rtmp.tls_listen` and `server.rtsp.tls_listen`, sharing `app` with their plain siblings. Either sibling may be off; `outputs.rtmp` or `outputs.rtsp` needs at least one of its two listeners.
  - **RTMPS play:** `rtmps://host:port/<app>/<name>`, the same play handler and caps as RTMP.
  - **RTMPS publish:** an input `rtmps://<the server's RTMPS address>/<app>/<key>?mode=listen`. It must name the server's RTMPS listener: a stream cannot open a TLS listener of its own, because the certificate is the server's. The default port of `rtmps://` is 443.
  - A plain `rtmp://…?mode=listen` input on the RTMPS address, and the reverse, are refused as an address conflict.
  - **RTSPS play:** `rtsps://host:port/<app>/<name>`, TCP only: a `SETUP` that offers only UDP is answered 461, even when `server.rtsp.udp` is on. R-D1's SRTP is M5c2.
  - The TLS handshake runs explicitly, first thing in the session's goroutine, bounded by the protocol's existing pre-session timeout (RTMP's `HandshakeTimeout`, `rtmp.DefaultHandshakeTimeout` = 5 s when zero; RTSP's `ReadTimeout`), never in an accept loop, after the existing pre-session caps admitted the connection. The RTMP handshake's own timeout starts after it.
  - **A failed handshake is visible** on all four TLS listeners: counted in `openstreamer_tls_handshake_failures_total{listener="https"|"api"|"rtmps"|"rtsps"}` and logged once, at debug, with the listener, the remote address and the reason. Debug, because a port scanner must not fill the log at info. A handshake cut short because the listener is closing or the server is stopping is neither counted nor logged. Everything else `net/http` reports (a panic in a handler, an accept error) is logged at error.
  - *If wrong:* a publisher that needs RTMPS on a second port waits for a per-listener certificate (R-S2).
- **R-S7 (TLS clients verify; the opt-out is in the scheme).**
  - `rtmps://` (pull and push; default port 443) and `rtsps://` (pull; default port 322) verify the peer against the system roots, with the URL's host as the server name. A private CA is added to the system store. On Linux and the BSDs it can also be named with `SSL_CERT_FILE`, which Go's `crypto/x509` reads there; on macOS and Windows Go uses the platform's store and ignores that variable.
  - **The opt-out is `rtmps+insecure://` and `rtsps+insecure://`.** It turns certificate verification off for that one URL and nothing else. It is not a default and no config key sets it globally. `+insecure` on any other scheme is refused, and so is `rtmps+insecure://…?mode=listen`.
  - Why the scheme: a stream's input and push are identified by their URL (`Pipeline.SetInputs`, the pushers' map), so the choice must be part of the URL; a query parameter cannot be used, because a push sends its query to the target verbatim (`rtmp.Config.KeepQuery`); a scheme is never sent to the peer (the `tcUrl` says `rtmps://`).
  - `pkg/rtmp` and `pkg/rtsp` know only `rtmps://` and `rtsps://` and a `*tls.Config`. The `+insecure` spelling is the product's, in `internal/ingest` and `rtmppush`.
  - `rtsps://` uses the TCP transport: `transport=udp` is refused at parse, `auto` means TCP.
  - A verification failure is an ordinary open failure: the input retries or fails over, the push backs off, and the error names the x509 reason and never the URL's secrets.
  - *If wrong:* the spelling is odd to someone used to a flag, and renaming it later is a config migration. IP cameras with self-signed certificates make some opt-out necessary.
- **R-S8 (closing a TLS connection never waits on the peer).**
  - **The premise.** `tls.Conn.Close` with a write in flight closes at once. **With no write in flight** it sends `close_notify` under its own 5 s write deadline. That second case is the real one: a media write misses its deadline and returns, the session fails and closes (`pkg/rtmp/session.go:416-423`, then `Close` at `:311`), the peer's buffer is still full, and the close takes 5 s.
  - **The mechanism,** one unexported `closeConn(c net.Conn) error` in `pkg/rtmp` and one in `pkg/rtsp`: for a `*tls.Conn`, `t := time.AfterFunc(100*time.Millisecond, func() { _ = raw.Close() })` with `raw = tc.NetConn()`, then `tc.Close()`, then `t.Stop()`. A healthy peer gets its `close_notify`; a stalled one costs 100 ms. Any other conn is closed directly.
  - **Many at once.** A loop that closes N sessions must not cost N × 100 ms: `rtmpsrv`'s play unregister (`registry.go:272-274`) closes its connections concurrently and waits for all of them, and `pkg/rtsp`'s `Server.Close` does the same.
  - **What keeps the raw connection.** `rtmpsrv`'s `admit` (`registry.go:595`, `context.AfterFunc(rt.ctx, func() { _ = c.Close() })`) and `ConnHook` are given the raw TCP connection, whose close is immediate; only `rtmp.Accept` gets the `*tls.Conn`.
  - **`net/http` is exempt, with a bound.** Its own close of a stalled TLS connection can take 5 s, in that connection's goroutine: a stream delete ends the HTTP-TS handler and waits on nobody. At stop, `Run` gives requests `shutdownWait` (2 s) as today, then closes the raw connections of the HTTPS listeners itself before `http.Server.Close`, so stop is delayed by at most `shutdownWait` whatever the readers do (Task 9a).
  - *If wrong:* a peer that reads slowly sees a truncated TLS stream at the end and logs it; no media is lost, because each protocol has its own end-of-stream message.
- **R-S9 (secrets).** An `rtmps://` or `rtmps+insecure://` URL is redacted exactly as an `rtmp://` one (the stream key cut to two characters, `redact.URL`, `redact.Masked`, the push scrubber, `logging.Scrub`). The key file's content is never read into an error, a log or a response; its path is not a secret.
- **R-S10 (the login limiter's per-address cap; controller ruling, revised after review round 2).** Today the limiter's key is address plus presented name (`internal/auth/limiter.go`), so one address inventing names gets a fresh key each time and can keep the 2 running and 16 waiting verification slots busy (`docs/REBUILD_PLAN.md` 1529–1533).
  - **The cap is one rule: at most 4 verifications in flight per client address** (`ClientKey`: the IP, an IPv6 address by its /64). A fifth is refused with 429 and `Retry-After: 1`. So one address holds at most 4 of the 18 slots.
  - **There is no per-address failure count and no per-address block.** Behind a shared address (a reverse proxy, a NAT, loopback) a block would let anyone lock every user out remotely, and a restart forgets the remembered logins that would have spared them.
  - **Its state is a small map of its own,** address to count, apart from the name table. An entry is removed when its count returns to 0, so the requests inside the login step bound it: it needs no eviction, no idle rule and no sweep.
  - **A refusal by the cap touches nothing else:** it is decided before the name key is looked up or inserted, so it evicts nothing from the name table (`TestLimiterRefusedReserveEvictsNothing` keeps passing).
  - **Remembered logins take no place:** the cap is consulted only where a verification would start.
  - Guessing one name's password stays bounded as today, by the name key's backoff and by PBKDF2 at 600 000 iterations.
  - *If wrong:* an attacker who sprays many names from one address is slowed only by each name's backoff and by PBKDF2's cost, at most 4 at a time; nothing stops the spray itself. Behind a reverse proxy every client shares one cap of 4, so a burst of first logins sees 429s with `Retry-After: 1`. The trusted-proxy setting that would tell clients apart moves to the backlog.

## Review Focus

1. **A rotation that is half done, and one behind a symlink.** The certificate file is replaced before the key file, or certbot retargets `live/` symlinks: the server keeps serving the old pair, counts one failure, logs it once without any key material, and takes the new pair on a later poll, with no restart and no session ended. *Pinned by Task 1's `TestStoreReloadKeepsOld` and `TestStoreWatchSymlink`, and Task 9b's `TestCertificateRotates`.*
2. **The wrong protocol, or silence, on a TLS port.** A plaintext RTMP or RTSP client on the TLS port, a TLS client on the plain port, a client that connects and sends nothing, and a client that stops mid-handshake: each is closed by the existing pre-session deadline, counted in the existing pre-session caps, never stalls the accept loop for other clients, and a plain HTTP request to the HTTPS port gets 400. *Pinned by Task 4's `TestServeTLSWrongProtocol`, Task 5's `TestRegistryTLSWrongProtocol` and Task 9a's `TestHTTPSWrongProtocol`, `TestHTTPErrorLog` and `TestTLSHandshakeFailedReported`.*
3. **A stalled TLS peer at teardown.** A player whose socket buffer is full while its stream is deleted or the server stops: after its write missed the deadline, its close returns within 300 ms, not `tls.Conn`'s 5 s, and 100 such players are closed in under 1 s (R-S8); a stalled HTTPS reader delays the server's stop by `shutdownWait` at most. *Pinned by Task 3's `TestTLSCloseStalled`, Task 4's `TestServeTLSCloseStalled`, Task 5's `TestRegistryTLSUnregisterStalled` and Task 9a's `TestHTTPTSOverTLS`.*
4. **A source whose certificate cannot be verified.** Self-signed, expired, or issued for another name: the pull or push fails with the x509 reason and no secret, retries as any failed open does, and is never silently accepted; `+insecure` accepts it for that URL only; `+insecure` on `rtmp://`, `http://` or a listen input is refused at validation. *Pinned by Task 3's `TestPlayTLSVerifies`, Task 6's `TestPushTLS`, Task 7's `TestParseTLSSchemes` and `TestTLSPullUntrusted`.*
5. **A stream key in an `rtmps://` URL.** `rtmps://h/live/<key>`, `rtmps+insecure://u:p@h/live/<key>?token=<t>` and `RTMPS://…`: the key, the password and the token are masked wherever an `rtmp://` URL's are, a masked URL is refused on the way back in, and the scheme is kept. *Pinned by Task 2's `TestURLTLSSchemes`, Task 6's `TestPushTLS` and Task 11's `TestM5c1NoSecretsLeak`.*
6. **The API on the network, and one address inventing names.** With `server.api.tls_listen` on a public interface, one address sends logins with thousands of invented names: at most 4 of them are ever being verified, the rest get 429, a real user from another address still logs in within a few verifications' time, a user already logged in from the attacker's own address keeps working, and when the flood stops that address logs in at once: nothing was blocked. *Pinned by Task 10's `TestLimiterAddressCap` and `TestAPIAddressCap`.*

### Task 1: `internal/certs`, the certificate in force

**Files:**
- Create: `internal/certs/certs.go`, `internal/certs/doc.go`, `internal/certs/certs_test.go`
- Create: `pkg/tlstest/tlstest.go`, `pkg/tlstest/tlstest_test.go`, `pkg/tlstest/doc.go`. It is under `pkg/` because the tests of `pkg/rtmp` and `pkg/rtsp` use it and `pkg/` never imports `internal/` (REBUILD_PLAN §3.7). It imports only the standard library and `testing`, a test helper beside `rtmptest` and `rtsptest`.

**Interfaces:**
- Produces:

```go
package certs

// Store is one certificate pair that can be read again while it is served.
type Store struct{ /* … */ }

// Load reads and checks the pair. Its errors name the file and the reason, never file content.
func Load(certFile, keyFile string) (*Store, error)
// Reload reads the pair again. On an error the pair in force stays. changed is false when the leaf is byte-identical.
func (s *Store) Reload() (changed bool, err error)
// Watch stats both files every interval until ctx ends and calls Reload when a size or a modification time
// differs from the last look, and on every tick while the latest Reload failed (R-S3); report gets each
// Reload's result. It returns when ctx ends.
func (s *Store) Watch(ctx context.Context, every time.Duration, report func(changed bool, err error))
// ServerConfig returns a config whose GetCertificate serves the pair in force: MinVersion TLS 1.2, nothing else set.
func (s *Store) ServerConfig() *tls.Config
// Info describes the pair in force and the reloads so far.
func (s *Store) Info() Info
type Info struct {
	NotAfter  time.Time // the leaf's
```

## Hand-over: M5c2

M5c2 starts from these facts of M5c1:
- An RTSPS session refuses UDP with 461 (`pkg/rtsp` `ServeTLS`, R-S6). SRTP adds `RTP/SAVP` offers to exactly that branch, with keys carried in the SDP that only a TLS session sees.
- The certificate store and the listener keys are not SRT's: SRT output encryption is a passphrase, as the input's is.
- `redact` treats the three RTMP schemes alike (`redact.RTMPScheme`); credentials in other URL paths have no rule yet.
- The config status and every stream document still return stored secrets to an editor (`?secrets=1`, `GET /api/v1/config`): write-only fields change that contract, not this plan.
