# M3b2 RTSP Output Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve every stream to RTSP players (ffmpeg/ffprobe, MediaMTX as a puller) over TCP interleaved and UDP, on our own `pkg/rtsp`, and check the output with `osconform`.

**Architecture:** `pkg/rtsp` gains the server side: our own H.264/H.265 RTP packetisers (single NAL unit and fragmentation units; RFC 3640 AAC already exists), SDP generation, RTCP sender reports and receiver-report parsing, and a server session core (OPTIONS, DESCRIBE, SETUP, PLAY, GET_PARAMETER, TEARDOWN) that sends RTP over TCP interleaved or from one UDP port pair per listener. `internal/mux/rtp` turns hub frames into RTP packets per track (per-session timestamp bases, parameter sets before every keyframe, resync after a loss, one stream-time NTP mapping for sender reports). `internal/output/rtspplay` serves players by stream name from the hub. `internal/conform` reads `rtsp://` with its own small frame rebuilder (independent of the ingest code it would otherwise share) so `osconform` checks the RTSP output.

**Tech Stack:** Go (`go 1.26.11`); `pion/rtp` (packet marshalling), `pion/sdp/v3` (SDP marshalling) — both already in `go.mod`; `pkg/h26x` (DTS from PTS in the conform reader); standard library; `stretchr/testify`. Test peers: ffmpeg/ffprobe (CI apt 6.1), MediaMTX 1.21.3 (the host-network RTSP container from M2c, pulling our output on demand).

**Spec:** [docs/REBUILD_PLAN.md](../../REBUILD_PLAN.md) §2 (Outputs: RTSP play), §3.3, §3.4 (RTP packetisers; parameter sets before each keyframe; epoch handling per muxer), §3.7 (`pkg/rtsp`, `pion/rtp`, `pion/sdp`), the M3 row and the M3b2 row of §5. References: RFC 2326 (RTSP 1.0), RFC 8866 (SDP), RFC 3550 (RTP/RTCP), RFC 6184 (H.264 payload), RFC 7798 (H.265 payload), RFC 3640 (AAC) — never another product's code.

**M3b2 exit criteria** (the M3 row restricted to RTSP; VLC-class clients are checked in M3b3 for every output): ffmpeg/ffprobe (TCP and UDP) and MediaMTX (as a puller) play our RTSP output for H.264+AAC and H.265+AAC; for the RTSP play output, `osconform`/`ReadRTSP` passes the steady-state, epoch-change, slow-consumer and B-frame scenarios and ffprobe reads it.

**Out of M3b2, with reasons** (ledger rulings at dispatch): RTSPS/SRTP (TLS, M5); play authentication and tokens (M6, as for RTMP play); multicast and RTSP over HTTP tunnelling (rare for players; add on demand); PAUSE, seek, `Scale`/`Speed` (live only: PAUSE answered 455); RECORD/ANNOUNCE (publishing into us is not a v2 input); RTSP 2.0; a mid-session codec change or a kind appearing (the SDP cannot follow: the session ends, players reconnect); VLC-class client checks (M3b3). M2c leftovers (backlog) are settled in Task 1.

**Spec deviation (ledger ruling at dispatch):** §3.4 says pion/rtp packetises H.264/H.265; this plan writes our own packetisers (`pion/rtp` still marshals packets) because pion's payloaders take Annex-B input (our NAL slices would be re-serialised and re-scanned), pion's H.265 payloader keeps its own parameter-set cache while §3.4 requires the output to insert every parameter set from `Config`, and we keep one MTU meaning across codecs. §3.7 already limits pion's payloaders to tests; Task 9 updates §3.4.

## Global Constraints

- Every Global Constraint of the M1, M3a, M2a, M2b, M2c and M3b1 plans still holds (independent libraries; `pkg/...` never imports `internal/...`; errors `pkg: op: %w`; never log and return the same error; every goroutine has a cancel path; hub writes never block — outputs read through `hub.Sub` only; parameter sets only in `Config`; peer tests via `internal/testpeer`; tests and CI never bind 554/1935/8554 nor touch other containers — a v1 soak runs on the dev machine).
- **Ownership:** every slice `pkg/rtsp` returns is a fresh allocation; `WritePackets`/`WriteRTCP` do not retain the caller's buffers after they return.
- **RTP origins (one owner):** the `pkg/rtsp` server draws, per SETUP'd track, a random SSRC, a random first sequence number and a random timestamp base `TSBase` (crypto/rand) and exposes them as `ServerSession.Origin(track)`; the `Transport` reply's `ssrc=` and PLAY's `RTP-Info` (`seq` = first sequence number, `rtptime` = `TSBase`, the RTP timestamp of stream time `b` on every track) come from it; `WritePackets` stamps SSRC and the next sequence number on every packet (callers never set them), so sequence numbers increase by one per packet with no server-made gaps. `b` is the session's first frame DTS (90 kHz). Video RTP timestamp = `TSBase + (PTS − b)`; audio = `TSBase + round((PTS_a0 − b)·rate/90000) + round((PTS − PTS_a0)·rate/90000)` with `PTS_a0` the track's first sent audio PTS (anchored rounding: no ±1 sample jitter from 90 kHz rounding) and rate the ASC core rate (the SDP clock; for implicit HE-AAC the core rate too). The marker bit is set on the last packet of each video access unit; for AAC as RFC 3640 says (last fragment of an AU). Stream time does not follow wallclock across an input outage, so SR NTP may drift from wallclock; only inter-track consistency matters.
- **Packetisation:** `MTU` means the RTP payload size everywhere (default 1200 bytes); `PacketizeAAC`, whose `mtu` bounds the whole RTP packet, is called with `MTU + 12`; H.264: single NAL unit or FU-A (RFC 6184 mode 1, `packetization-mode=1`); H.265: single NAL unit or FU (RFC 7798, no DONL); AUD and filler NAL units dropped; every parameter set of `Config` (VPS, SPS, PPS) sent as single NAL units at the start of every keyframe access unit, before its slices, with the keyframe's timestamp (§3.4). AAC: RFC 3640 AAC-hbr (`sizelength=13;indexlength=3;indexdeltalength=3`), one AU per packet (fragmented above the MTU). Packets of one frame go out in one `WritePackets` call (one write deadline per frame, not per packet).
- **SDP** (DESCRIBE): one media per carried track, `a=control:trackID=<n>` relative to `Content-Base: rtsp://<host>/<app>/<name>/`, `a=control:*` at session level; H.264 `a=rtpmap:96 H264/90000`, `a=fmtp:96 packetization-mode=1;profile-level-id=<from SPS>;sprop-parameter-sets=<SPS>,<PPS>`; H.265 `a=rtpmap:97 H265/90000`, `a=fmtp:97 sprop-vps=…;sprop-sps=…;sprop-pps=…`; AAC `a=rtpmap:98 mpeg4-generic/<rate>/<channels>`, `a=fmtp:98 streamtype=5;profile-level-id=1;mode=AAC-hbr;sizelength=13;indexlength=3;indexdeltalength=3;config=<ASC hex>`; `a=range:npt=now-`. The SDP's tracks are the stream's current carried tracks: the lowest-numbered live hub track of each kind (video, audio); others skipped, counted. Content-Base = the request's scheme://host[:port] as sent + the normalised path + `/` (query dropped); RTP-Info `url=` is each SETUP request URL byte for byte (ffmpeg matches it with `strcmp`); the tracks are frozen at the session's first SETUP.
- **Sender reports:** every 5 s per track and once right after each track's first RTP packet of the session (so pull clients align at once); one NTP mapping per session from stream time — NTP(t) = NTP₀ + (t − b)/90000 s with NTP₀ the wallclock at the session's first packet — so every track's SR maps equal stream times to equal NTP instants; the SR's RTP timestamp and NTP are those of the track's last sent packet; packet and octet counts per track. When the server ends a session it sends, per SETUP'd track on that track's RTCP channel or port, one compound RTCP packet SR + SDES (CNAME) + BYE (ffmpeg reaches EOF only after a BYE on every stream); only `ServerSession.Close` sends BYE; the server builds the compound as the track's last SR passed to `WriteRTCP` (or an empty RR when none was sent) + SDES + BYE.
- **Start, resume and epochs:** a TCP session subscribes with `hub.SubscribeCached` (GOP replay; TCP backpressure paces it); a UDP session subscribes with `hub.SubscribeLive` (no GOP replay; gated at the next live keyframe — a replay at line rate would overflow the client's UDP receive buffer). A session's first delivered frame is a video keyframe when the session carries video, else audio; audio with PTS below the first keyframe's PTS is dropped (counted `dropped_early_audio`); after `Delivery.Lost > 0` the muxer drops frames until the next video keyframe (the parameter sets go before it as always) and drops early audio again; RTP timestamps stay continuous across epochs because hub stream time is continuous (Clock invariant), so an epoch change needs nothing beyond in-band parameter sets before the next keyframe; a frame with DTS below `b` is dropped (counted `dropped_before_base`).
- **Codec changes:** when an epoch changes a carried track's codec, changes a carried AAC track's ASC, sampling rate or channel count (RFC 3640's `config=` and the rtpmap clock exist only in the SDP), or a frame arrives whose kind (video or audio) is absent from the session's frozen SDP, the play output ends the session (BYE, close; players reconnect and DESCRIBE again). A frame of a kind the SDP lists but from another hub track, or from a listed track the client did not SETUP, is ignored and counted. Video resolution and parameter-set changes within a codec only change the in-band parameter sets.
- **Paths:** a player's URL is `rtsp://<host>:<port>/<app>/<name>` where app is given to the server once (osdev flag `-rtsp-play-app`, default `live`) and name is the server's stream name; track URLs append `/trackID=<n>`. Paths are normalised before lookup: query dropped, trailing `/` dropped, a `/trackID=<n>` suffix split off. Unknown name, a stream that is not live (`hub.Live()` false or no live track configs), and every cap are answered `404 Stream Not Found` with the same text.
- **Session behaviour (`pkg/rtsp` server):** requests are answered in order per connection with the request's `CSeq`; session IDs are ≥ 16 random hex characters; `Session: <id>;timeout=60`; a session always ends when its RTSP connection closes (both transports); a UDP session also ends after 60 s without a request or an RTCP packet from the client; a TCP session stays alive while its connection is open (the write deadline catches dead peers); GET_PARAMETER and OPTIONS answer 200; TEARDOWN ends the session; status codes: unknown or missing Session 454, PLAY before SETUP or SETUP after PLAY 455, PAUSE 455, RECORD/ANNOUNCE 405 with `Allow`, unsupported transport 461, unknown methods 501, a bad or missing CSeq 400; PLAY on a track URL is treated as aggregate; `Public: OPTIONS, DESCRIBE, SETUP, PLAY, GET_PARAMETER, TEARDOWN`. PLAY's response (`Range: npt=now-`, `RTP-Info` from the origins) is written and flushed before the handler's `Play` starts. `$` frames from the client (RTCP) are parsed (liveness); anything else on the interleaved stream is resynchronised like the client does.
- **Transports:** the server walks every comma-separated offer in `Transport` and takes the first it supports; profiles `RTP/AVP`, `RTP/AVP/UDP` and `RTP/AVP/TCP` match case-insensitively; `mode=record` and any `destination=` other than the peer are refused (461). TCP interleaved (`interleaved=a-b` — the client's channels if free, else the next free even pair, answered in the reply) and UDP unicast (`client_port=p-q` echoed, answered with `server_port=` of the listener's single RTP/RTCP port pair and `ssrc=`; packets are sent from that pair to the RTSP connection's peer IP and the client's ports; inbound RTCP on the pair is matched to a session by source address and port; packets on the RTP socket (clients' NAT punches) are read and discarded). One session uses one transport for all its tracks.
- **Bounds (`pkg/rtsp` server, `ServerConfig`, defaults when zero):** request header ≤ 64 KiB, body ≤ 64 KiB; read timeout per request 10 s until PLAY; a connection without a playing session lives at most 30 s; write timeout 10 s per `WritePackets` call (a session that misses it ends); connections without a playing session ≤ 64 per listener and ≤ 4 per IP (IPv6 by /64); playing sessions ≤ 256 per stream (checked at PLAY), 1024 per listener, 64 per IP; at most 8 tracks per session; one session per connection.
- **Queues:** TCP sessions subscribe with `hub.SubscribeCached(name, 256)` (the GOP replay always fits); UDP sessions with `hub.SubscribeLive(name, 256)`; a UDP session has no backpressure, so loss shows as `Lost > 0` only when its hub queue overflows. Test readers set a 4 MiB UDP receive buffer (`pkg/rtsp` client does so best effort, as `internal/ingest/udp.go` does).
