# M5c2b: SRTP for RTSP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** With `server.rtsp.srtp` on, every session of the RTSPS listener carries SRTP keyed by SDES inside TLS, over UDP and over the interleaved channel, and an RTSP pull whose SDP carries an SDES key is decrypted; with it off nothing changes.

**Architecture:**
- **`pkg/srtp` is a new package on the standard library:** one suite (`AES_CM_128_HMAC_SHA1_80`), SRTP and SRTCP, the RFC 3711 key derivation, index estimation and replay window, and RFC 4568's `a=crypto` text. It knows nothing of RTSP.
- **`pkg/rtsp` protects at the socket edge.** The server draws one key per track when it answers `DESCRIBE` on a TLS connection, writes it into the SDP, and protects in `WritePackets`, `WriteRTCP` and the BYE; the handler (`rtspplay`) is not told. The client reads the keys from the SDP and unprotects where a datagram or an interleaved frame arrives, before anything parses it.
- **The SDP selects SRTP, not `SETUP`** (R-P4, R-P5), because ffmpeg offers `RTP/AVP` for a session described as `RTP/SAVP`.
- **The hub is untouched.** Pulled media is decrypted before the depacketizer; played media is encrypted after the muxer.

**Tech Stack:** Go 1.26, stdlib `crypto/aes`, `crypto/cipher`, `crypto/hmac`, `crypto/sha1`, `crypto/subtle`, `crypto/rand`; `pion/rtp` and `pion/sdp` as today. Peers: ffmpeg 8 on the host; ffmpeg 6.1, VLC 3.0.20 and GStreamer 1.24 in `osv2-ci-peers:m4a`.

**Spec:**
- `docs/REBUILD_PLAN.md`: the M5c2b row (line 853); the "Out of" rows that name M5c2b (923, 1263, 1396, 1573, 1689); the hand-over facts (1584–1601); §3.7 Libraries (749).

## Rulings (R-P)

Each ruling ends with what it costs if it is wrong.

- **R-P1 (scope and exit criterion).** M5c2b is done when:
  1. with `server.rtsp.srtp` on, ffmpeg 6.1 and 8 play `rtsps://` over UDP, over the interleaved channel and with no transport named, against our server, and decode every frame with `-xerror`;
  2. our client pulls the same stream from our server over `rtsps://` with `transport=tcp` and with `transport=udp`, and the pulled stream's HLS passes `conform`;
  3. with `server.rtsp.srtp` off, every test that exists at HEAD da63d64 passes unchanged;
  4. a packet under a wrong key, a tampered packet and a replayed packet are dropped and counted on both sides, and no input of any shape panics;
  5. no key appears in a log (debug level included), a metric, an error, a status or an API response.
  - *If wrong:* a criterion is added; nothing built here is undone.
- **R-P2 (library).** `pkg/srtp` is written from RFC 3711 and RFC 4568 on the standard library. pion/srtp is not approved; nothing is copied from another product. One suite, `AES_CM_128_HMAC_SHA1_80`. `AES_CM_128_HMAC_SHA1_32`, AES-256 and AES-GCM (RFC 7714) are backlog.
  - *Why:* it is the one suite every measured peer speaks, and the project's rule is its own libraries.
  - *If wrong:* a camera that offers only the 32-bit tag is skipped with a reason (R-P12); a suite is one more tag length or one more cipher in one package.
- **R-P3 (opt-in).** `server.rtsp.srtp` is a bool, default false, and needs `server.rtsp.tls_listen`. It is a server key: a change needs a restart, as every server key does. With it on, GStreamer (MIKEY only) cannot play the RTSPS listener; the plain listener still serves it. MIKEY is backlog.
  - *If wrong:* the default flips in one line; M5c1's rows run with it off either way.
- **R-P4 (what carries SRTP).** A connection of `ServeTLS` on a server with `ServerConfig.SRTP` is an *SRTP connection*: its `DESCRIBE` answer says `RTP/SAVP` with one `a=crypto` per media, and every session it sets up is SRTP, interleaved included. A connection of the plain listener is never one: a key travels only inside TLS. Nothing is chosen per request.
  - *Why:* ffmpeg decrypts on TCP too once the SDP has `a=crypto` (measured), so one SDP cannot serve both.
  - *Cost:* an interleaved RTSPS session is encrypted twice.
  - *If wrong:* a per-request choice needs a second SDP form; no stored state depends on this.
- **R-P5 (`SETUP`).** On an SRTP connection the profile offered does not select anything:

  | Offer | Answer |
  |---|---|
  | `RTP/AVP/TCP`, `RTP/SAVP/TCP` | 200, interleaved, the offered profile echoed |
  | `RTP/AVP`, `RTP/AVP/UDP`, `RTP/SAVP`, `RTP/SAVP/UDP` with `client_port` | 200 over UDP when the server owns a pair (R-P6), the offered profile echoed; else the next offer, else 461 |
  | any, on a connection whose last `DESCRIBE` was not for this path | 455: the client holds no key |
  | a `KeyMgmt` header | ignored |

  On every other connection `RTP/SAVP*` is 461, as at HEAD.
  - *If wrong:* a player that needs `RTP/SAVP` refused, or MIKEY, is no worse off than today.
- **R-P6 (UDP).** `server.rtsp.udp` binds the one UDP pair. It serves the plain listener's sessions as today and an SRTP connection's sessions; a TLS connection without SRTP still gets 461. `udp` is valid with `listen`, or with `tls_listen` and `srtp`. The pair binds on the plain listener's host when there is one, else on the TLS listener's; with `udp`, `srtp` and both listeners, the two hosts must be equal.
  - *Why:* one pair cannot send from two addresses, and a pair on loopback cannot reach an RTSPS player elsewhere.
  - *If wrong:* a second pair per listener; the validation rule then goes.
- **R-P7 (keys).** One fresh master key and salt per track, from `crypto/rand`, drawn at `DESCRIBE` and frozen by the session's first `SETUP` with the SDP's descriptors. RFC 4568 §6.1 wants every master key in an SDP unique. A second `DESCRIBE` before `SETUP` draws new keys; a `DESCRIBE` of the session's path after `SETUP` repeats the session's keys. A key is never logged and never reaches a metric, a status or an error: `srtp.Keys` formats as `srtp.Keys(hidden)` under every verb and has no exported field or accessor, and it and `srtp.Context` are held by pointer only (a pointer field prints as an address). The SDP body is never logged, by M5c2a's rule.
  - *If wrong:* one key per session is the same code with one draw.
- **R-P8 (lifetime).** No MKI, no rekey, key derivation rate 0. A key lives as long as its session. `Protect` refuses with `ErrExhausted` at 2^48 SRTP packets or 2^31 SRTCP packets per source, which ends the session. The ROC starts at 0 on both sides, and an SRTP track's first sequence number is drawn below 2^15 (RFC 3711 §3.3.1), so reordering around the first packets cannot put the receiver one ROC behind.
  - *Cost:* a pull that joins a source whose key has run past 65536 packets fails authentication (SDES signals no ROC); our server keys per session, so it never does that to a player.
  - *If wrong:* rekey needs MKI or a new `DESCRIBE`; neither is closed off.
- **R-P9 (SSRC).** Each track keeps its own random SSRC, as at HEAD, and its own `srtp.Context`. A context keeps state per SSRC, for at most 8 sources each way, made only by a packet that authenticated. The pull client's report SSRC is redrawn while it equals the `ssrc=` of a `SETUP` reply, since both ends use one key and the SSRC is what keeps their keystreams apart.
  - *If wrong:* a source with more than 8 SSRCs under one key is dropped and counted; the cap is a constant.
- **R-P10 (RTCP out).** On an SRTP session every RTCP the server sends is SRTCP with the E flag set: the sender reports and the BYE compound. The first SRTCP index is 0.
- **R-P11 (RTCP in).** On an SRTP session only an authenticated SRTCP packet is a sign of life. A well-formed plain report is dropped and counted `plain`; a packet that fails authentication is counted `auth`; a replay `replay`. None ends a session. An RTSP request keeps a UDP session alive as today, and ffmpeg sends one every half timeout.
  - *Why:* an unauthenticated datagram must not hold a session open, and the handover says keep-alives hold ffmpeg either way. Task 0 measures both.
  - *If wrong:* Task 0's stop rule says so before the server is built; the change is one branch (a plain report also touches).
- **R-P12 (pull: what is decrypted).** Per media, the first `a=crypto` line that parses with the supported suite is used, whatever the scheme (`rtsp://` or `rtsps://`) and whatever the `m=` profile (`RTP/SAVP`, or `RTP/AVP` as ffmpeg writes it). A media that says `RTP/SAVP` with no `a=crypto`, or whose `a=crypto` lines are all unsupported (another suite, an MKI, two keys, a session parameter other than `KDR=0` and `WSH=`), is unsupported with a reason that quotes nothing, and the other media play. A lifetime (`|2^20`) is accepted and ignored. A session-level `a=crypto` is ignored. `SETUP` offers the profile the `m=` line named.
  - *Why:* a key that came in clear is the source's choice; refusing it yields no media and no security.
  - *If wrong:* a refusal for `rtsp://` is one condition.
- **R-P13 (pull over UDP).** `rtsps://…?transport=udp` is accepted at parse. After `DESCRIBE`, when a usable media carries no SDES key, `Dial` fails with `rtsp: dial: rtsps over udp needs SRTP in the SDP` before any `SETUP`: RTP never leaves TLS in clear. `auto` on `rtsps://` stays TCP, as at M5c1.
  - *If wrong:* `auto` may try UDP later; it is no worse than M5c1 now.
- **R-P14 (failures).** A packet that fails is dropped and counted and changes no state; it never ends a session. A pull that saw failures and never one authenticated packet ends at the idle timeout with `rtsp: read: srtp: no packet passed authentication` in place of the idle error, and restarts as any failed input does.
- **R-P15 (counters).**
  - Server: `openstreamer_rtsp_srtcp_dropped_total{reason="auth"|"replay"|"plain"}`, written only when `server.rtsp.srtp` is on.
  - Pull: the reader's stats gain `srtp_auth_failures` and `srtp_replays` (SRTP and SRTCP summed) only for a session with an SRTP media, and `/metrics` gains `openstreamer_stream_input_srtp_dropped_total{name,reason="auth"|"replay"}` only while those keys are present.
  - *If wrong:* names are renamed before M7's dashboards exist.
- **R-P16 (API).** The OpenAPI document does not change: the config travels as YAML text and the reader's stats are not in a response. The config gains one key.
- **R-P17 (multicast).** There is none: `selectTransport` skips every multicast offer, and that stays.
- **R-P18 (the parked N1).** The fix is in `redact.settle` and `config`'s `commentLine`, as the M5c2a reviewer proposed, and both views then show `redact.URL`'s form of the four shapes. `logging.Scrub` stays by token: a log line is prose, and judging the rest of a line would swallow the reason after every URL. The four shapes are pinned where a URL reaches a log, which is always through `redact.URL` on the whole value.
  - *If wrong:* a log line that quotes such a URL unredacted shows the tail of its secret; that row stays in the Backlog under `logging`.
- **R-P19 (proof without an SDES server).** No peer serves SDES over RTSP. The pull client is proved against `rtsptest` (which gains SRTP), against our own server, and transitively against ffmpeg: `pkg/srtp` unprotects what ffmpeg's `srtp://` output sends, and ffmpeg decodes what our server protects.
- **R-P20 (sizes).** The muxer's payload size stays 1200: a packet grows by 10 bytes and an RTCP packet by 14, well under any path MTU.

## Review Focus

1. **A session longer than 65536 packets, with loss and reordering.** A 4 Mb/s video wraps its sequence number in about three minutes. Across the wrap, with packets lost, swapped and late, every genuine packet still authenticates, on the first wrap and the second. *Pinned by Task 2's `TestIndexAcrossWrap` and Task 6's `TestSRTPClientServerLong`.*
2. **Hostile datagrams.** A wrong key, a flipped bit anywhere, a replay, a truncated packet, an empty datagram and random bytes, on the UDP ports and the interleaved channel, at the server and at the client: dropped, counted, no panic, no state moved, the session goes on, and an unauthenticated packet never keeps a session alive. *Pinned by Task 2's `TestTamper`, `TestReplay` and `FuzzUnprotect`, Task 3's `TestServerSRTCPInbound`, and Task 4's `TestClientSRTPTamper` and `TestClientSRTPWrongKey`.*
3. **Players that are not ffmpeg.** `SETUP` with `RTP/SAVP`, `SETUP` without `DESCRIBE`, `DESCRIBE` twice, `DESCRIBE` after `SETUP`, a `KeyMgmt` header, `RTP/SAVP` asked of the plain listener: each is answered by R-P5's table, an SRTP session never sends one plain RTP or RTCP packet, and no session runs under a key its client was not given. *Pinned by Task 3's `TestServerSRTPSetup`, `TestServerSRTPDescribe` and `TestServerSRTPNeverPlain`.*
4. **A key that leaks sideways.** `%v`, `%+v`, `%#v`, `%x` and slog of a key and of the structs that hold one; the error for a bad `a=crypto`; a media's skip reason; `rtsptest`'s records; debug logs, `/metrics`, statuses and API responses while a session plays. *Pinned by Task 2's `TestKeysHidden` and `TestParseCryptoErrorsQuoteNothing`, Task 4's `TestParseSDPCrypto`, and Task 7's `TestM5c2bNoKeysLeak`.*
5. **SDPs that are not ours.** `a=crypto` under `RTP/AVP`; a lifetime; an MKI; unsupported suites listed before the supported one; session parameters; `RTP/SAVP` with no key; a key on plain `rtsp://`: a usable key decrypts, anything else skips that media with a reason, and garbage never reaches a depacketizer. *Pinned by Task 2's `TestParseCrypto` and Task 4's `TestParseSDPCrypto` and `TestClientSRTPForms`.*

- The rules the signatures do not say:
  - **RTP.** Version 2 or `ErrMalformed`. The encrypted part is the payload after the fixed header, the CSRCs and the extension; padding is left as it is. The tag is over the header, the encrypted payload and the 32-bit ROC.
  - **Index (RFC 3711 §3.3.1 and Appendix A).** Per SSRC, ROC 0 and `s_l` the first sequence number seen; the receiver moves `s_l` and the ROC only after the tag is checked, and the sender estimates the same way from the highest sequence sent. `ErrExhausted` when the ROC would pass 2^32 − 1.
  - **RTCP.** The first 8 bytes are clear, the rest encrypted; then the E flag and the 31-bit index; then the tag over all of it. The sender's index starts at 0, one per SSRC, and `ErrExhausted` ends it at 2^31. A received packet with E clear is accepted when its tag is right.
  - **Replay.** A 64-packet window per SSRC, one for SRTP and one for SRTCP. A packet below the window or seen before is `ErrReplay`.
  - **Order of checks in Unprotect:** shape, replay against the estimated index, tag (`subtle.ConstantTimeCompare`), then decrypt and move the state.
  - **Sources.** State for an SSRC is made by `Protect`, or by an `Unprotect` whose tag passed; the ninth is `ErrSources`.
  - **`ParseCrypto`.** Fields are split at spaces and tabs. The tag is 1 to 9 digits and not 0. The suite is compared exactly. The key method is `inline:`; the base64 is exactly 40 characters of the standard alphabet (30 bytes, which never pad). `|<lifetime>` is accepted and ignored; `|<mki>:<len>` and a second key after `;` are `ErrSuite`. Session parameters: `KDR=0` and `WSH=<n>` are ignored, any other is `ErrSuite`. Everything else is `ErrCrypto`.

## Hand-over: M6

M6 (DVR and timeshift, auto-publish, templates, sessions and tokens, webhooks) starts from these facts.

- **The hub sees no SRTP.** A pull is decrypted before the depacketizer and a play is encrypted after the muxer, so DVR, timeshift and every packager are unaffected.
- **A key is handed out at `DESCRIBE`,** before `SETUP` and `PLAY`. A play token for RTSP must therefore be checked at `DESCRIBE` as well as at `SETUP`; checking it at `PLAY` only would give an SDP, keys included, to a caller without a token. The key is useless without the media, but the stream's codecs and parameter sets are in that SDP.
- **SRTP is a server key, not a stream key.** A template cannot turn it on per stream, and an auto-published stream is served by the listeners as they are configured.
- **A session knows whether it is SRTP** (`rtsp.ServerSession.SRTP()`), for M6's per-session records. A webhook or a session record must never carry an SDP body or a `Transport` reply's neighbours that hold keys; nothing but the SDP holds one today.
- **Counters:** `openstreamer_rtsp_srtcp_dropped_total{reason}` (server-wide, only with SRTP on) and `openstreamer_stream_input_srtp_dropped_total{name,reason}` (per stream, only for an SRTP pull). Per-stream play sessions are still M6's.
- **`rtsps://` pulls may now use UDP** (`?transport=udp`), and fail closed with `rtsps over udp needs SRTP in the SDP`; a template that sets `transport=udp` for RTSPS sources gets that error from a source without SDES.
- **Left open, in the Backlog:** MIKEY (GStreamer, MediaMTX); the `SHA1_32`, AES-256 and GCM suites; rekey and MKI; `auto` trying UDP on `rtsps://`; `logging.Scrub` and the rest of a line.
- **Measured, filled in by Task 8:** Task 0's P1 to P4 on ffmpeg 6.1 and 8; `BenchmarkProtectRTP`'s ns/op and allocs/op.
